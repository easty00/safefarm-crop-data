## 1. 결정된 것과 그 이유

### 1-1. 계산식 — Modified GDD (Tmax·Tmin 개별 클램프)

```
Tmax' = min(Tmax, Tupper)      상한이 없으면(None) 자르지 않는다
Tmin' = max(Tmin, Tbase)
GDD   = max( (Tmax' + Tmin')/2 − Tbase , 0 )
```

**⚠ 2026-09-16 에 되돌렸다.** 중간에 FAO56rev 식 (2)(평균을 먼저 내고 그 평균을 자르는 것)
로 바꿔 적었다가, 2026-09-14 에 이미 정해 둔 이 식으로 되돌렸다. 아래 §1-1a 에 경위가 있다.

**왜 이것인가**

- **상한을 아는 작물만 저절로 걸린다.** `upper_temp` 가 비면 자르지 않으므로
  일반 GDD 와 결과가 같아진다. 식을 작물마다 갈아끼울 필요가 없다 —
  **코드에는 이 식 하나만 넣고, 갈리는 것은 `crops.upper_temp` 데이터뿐이다.**
- 국내 실증 사례가 이 방식이다. 옥수수 출사기 예측 오차 7~10일 → 2~3일,
  고랭지 배추 결구 정지 구간 판별 (`보관/gdd 관련 대화 기록.md` §국내 적용 사례).
- 폭염일이 늘면서 Standard 가 "열은 쌓였는데 작물은 안 자란" 오차를 키웠다.
  그 보정이 이 식의 목적이다.

**⚠ 이름이 비슷한 다른 식과 헷갈리지 말 것**

| | 자르는 순서 | 옥수수 폭염일(36/24) | 상추 봄날(18/2) |
|---|---|---|---|
| **Modified (채택)** | Tmax·Tmin 각각 → 평균 | 17.00 | 7.00 |
| FAO56rev 식 (2) | 평균 → 그 평균을 자름 | 20.00 | 6.00 |

한 철(90일) 쌓으면 옥수수 폭염 −15%, 상추 봄 +17% 로 갈린다. **작은 차이가 아니다.**

**다른 방식을 쓰지 않는 이유**

| 방식 | 왜 안 쓰나 |
|---|---|
| 식 (1) Standard `max(Tavg−Tbase, 0)` | 상한이 없다. 호냉성 채소는 25℃ 넘으면 실제로 생육이 멈추는데 계속 쌓인다 |
| FAO56rev 식 (2) | 평균을 낸 뒤 자르면 **더운 낮의 정체가 서늘한 밤에 가려진다.** Tmax 36 이어도 Tmin 이 낮으면 평균이 상한 아래라 안 잘린다 |
| 조건부 전환 (평상시 Standard / 폭염시 Modified) | **명시적으로 기각.** §6-10 참조. ⚠ 그건 **날마다** 식을 바꾸는 것이라 이 절과 다른 얘기다 — 여기는 식 하나를 고정으로 쓰고 데이터만 갈린다 |

### 1-1a. ⚠ 이 절이 두 번 뒤집혔다 — 경위를 남긴다

```
2026-09-14  Modified 채택. "식 하나 + 작물마다 upper_temp, 없으면 무한대"
            (대화기록 693aceff · docs/대화기록_복구_693aceff.md 1371~1383줄)

2026-09-15  FAO56rev 식 (2) 로 바꿔 적음
            근거 ① Paredes(2025) 표가 식 (2) 전제로 모은 값이다
            근거 ② "MRCC 는 옥수수 전용 관행이고, 상추에 쓰면
                    Tmin 을 4.4 로 끌어올려 거의 안 쌓인다"

2026-09-16  Modified 로 되돌림 (사용자 결정)
            ⚠ **근거 ②가 계산을 반대로 했다.** Tmin 을 끌어올리면 평균이 올라가
              **더** 쌓인다. 상추 봄날 Standard 6.0 → Modified 7.0 (+17%).
              같은 문서 §6-10 의 자기 예시도 더 쌓인다고 적고 있었다.
              "거의 안 쌓인다" 는 틀린 문장이었고, 그걸 근거로 뒤집었던 것이다.
```

**근거 ①은 남는 문제다.** Paredes(2025) 표는 식 (2) 를 전제로 모은 값이 맞다.
그래도 Modified 를 쓰기로 한 까닭 —

```
· Tbase·Tupper 는 '그 작물이 언제 자라고 언제 멈추나' 의 생리값이라
  두 식 사이에서 뜻이 달라지지 않는다. 달라지는 것은 누적량이지 값의 정의가 아니다
· gdd_target 을 **우리가 역산해서 만든다.** 목표값과 누적식이 같은 자로 재지면
  둘의 짝은 맞는다 — 논문의 목표값을 가져다 쓰는 게 아니다 (§C 는 전부 역산 대상)
· 국내 폭염 실증이 Modified 쪽이다
```

⚠ **그러므로 역산과 운영은 반드시 같은 식이어야 한다.** 역산을 식 (2) 로 하고
  운영을 Modified 로 하면 목표값이 통째로 어긋난다. §5-3 에 적어 두었다.

### 1-2. 일평균 정의 — (Tmax + Tmin) / 2

```
Safe-farm 스키마가 주는 것    temp_max · temp_min 뿐
논문·MRCC 가 쓰는 정의        (Tmax + Tmin) / 2        ✅ 일치
기상청 일평균                 24시간 관측값의 평균       (스키마에 없음)
```

우연히 맞은 게 아니라 **확인해서 맞은 것**이다. 정의가 다르면 Tbase 를 그대로 못 쓴다.
맑은 날은 (Tmax+Tmin)/2 가 24시간 평균보다 0.3~1.0℃ 높게 나온다.

일본 자료를 쓸 때는 이게 문제가 된다 — 일본 기상청도 24시간 평균이다. §4-3 참조.

### 1-3. 누적 방식은 ③ (GDD, 빼는 방식) 하나로 통일

로드맵 §1 의 ①②③ 중 ③이다. `sum_method` 컬럼은 만들지 않는다.

**왜 ②를 안 쓰나** — 국내 1차 목표값(벼 1,100~1,200 등)이 전부 ② 단위이고 ②를 쓰면
그 출처를 살릴 수 있다. 그런데 본선 작물 대부분은 어차피 목표값을 역산해야 한다.
②의 이점이 벼 하나에만 남는데, 컬럼 하나와 분기 로직을 더할 값어치가 없다.

**벼도 ③으로 간다.** 1,100~1,200 을 다시 역산해 `confirmed=N` 이 되지만, 정확도가
떨어지는 게 아니라 출처 딱지만 바뀐다.

### 1-4. 스키마 변경 — 컬럼 하나 + 표 하나

```sql
ALTER TABLE crops ADD COLUMN upper_temp NUMERIC(4,1);   -- nullable
```

⚠ **2026-09-16 에 표가 하나 더 늘었다.** 작성 당시에는 컬럼 하나뿐이었다.

```
crop_disaster_rules   작물 · 생육단계 · 임계온도 → 재해 경보 판정
                      ORM 초안 = pipeline/제안_crop_disaster_rule.py
                      ⚠ 저쪽의 기존 `disaster_rules` 와 **다른 표다.**
                        저쪽은 관측소별 절기 기상 통계, 이쪽은 작물 생리 기준
```

⚠ **`out/스키마/crops.csv` 에는 `upper_temp` 칸이 없다.** 저쪽 ORM 이 받는 칸만 내기
  때문이다. 값은 `out/스키마/근거/crops.csv` 에 있다. 위 ALTER 를 먼저 하고
  `build.py` 의 `계약["crops.csv"]` 에 칸을 더해야 따라간다 (작업기록 §5).

`base_temp` · `gdd_target` · `crop_stages` 는 손대지 않는다.
출처와 `confirmed` 는 DB 가 아니라 별도 CSV 로 관리한다 — 계산에 쓰이는 값이 아니다.

### 1-5. 작형은 컬럼이 아니라 파종일이 정한다

배추를 8월에 심으면 가을배추, 5월에 심으면 고랭지 작형이다. **사용자가 파종일을 주면
작형은 저절로 정해지므로 별도 칸이 필요 없다.**

그래서 `선정작물/결과/crops_초안.csv` 의 22작형 표는 `crops` 테이블의 행이 아니라
**"언제 심으면 되나" 추천값** 으로 쓴다.

### 1-6. 숙기(maturity_type) — 3분할은 셋만

```
3분할  벼(논벼) 370품종 · 감자 46 · 양파 40        근거 충분
MID 하나  나머지 11작물                            근거 없음
```

상추 9품종은 전부 '중생' 이고, 배추 2·수박 3·마늘 3·토마토 5·고추 1 은 갈래가 하나뿐이다.
없는 걸 지어내지 않는다. 근거가 생기면 그때 행을 추가한다.

## 2. 선정한 작물

**선정 기준** (순서대로 적용)

```
① 적산온도 모델이 성립하나   → 과수 전체·마늘 탈락 (로드맵 §6-4)
② 노지가 주류인가          → 오이·참외 탈락 (§6-5 시설재배 제외)

```

⚠ **딸기는 ②에서 탈락시켰다가 2026-09-16 에 되살렸다.** 작형을 안 보고 작물
  이름만으로 "딸기=시설" 이라고 단정한 것이 잘못이었다. 농사로에 등록된 문서는

```
딸기(사계성여름재배)   cntntsNo 30609   ← 노지. 이것만 받아 두었다
                    촉성·반촉성이 시설이고, 이건 그쪽이 아니다
```

  **작물이 아니라 작형으로 갈라야 한다.** 고추·수박·방울토마토도 같은 이유로
  작형을 못 박아 둔 것이다 (아래 '작형 지정이 중요하다').

**⚠ 마늘은 ①에서 탈락 대상인데 재배면적 때문에 넣었다.** 저온요구도 작물이라
적산온도로 안 풀린다(쪽 분화에 5℃ 이하 30일 이상). **마늘만 적산 진행률 대신
달력 + 재해 경보로** 다루는 게 맞다. 미결이다.

⚠ **작물 목록과 수를 여기에 적지 않는다.** 한 번 적었다가 작물을 줄이자
  20개 파일 70여 곳이 한꺼번에 낡았다. 정본은 등록표 하나다.

```bash
python pipeline/crops.py       지금 등록된 작물 · 문서 · 본선 여부
```

작형 표는 `작물_확정표.md` §A 에 있다.

**2026-09-16 에 넷을 버리고 둘을 되살렸다.**

```
버림   당근 · 파 · 쪽파 · 가지
       다섯 원본 날 자료를 전수로 세어 정했다. 안 읽어서가 아니라 원본에 없다.
       재해·단계·고온·경보·숙기가 모두 0이고 달력밖에 못 준다.

되살림  딸기 · 옥수수
       확정표에 줄이 없다는 이유로 빼 두었던 것인데, 그건 뺄 이유가 아니라
       **확정표에 줄을 더할 일**이었다. §B-1·§B-2 에 논문값으로 채웠다
       옥수수 base 10 은 국내 1차 자료다 — "10℃ 이하에서 생육정지"
```

**작형 지정이 중요하다.** 같은 작물에 시설 작형이 섞여 있어서 이름만 쓰면 안 된다.

## 4. 판단의 근거 — 왜 이렇게 정했는지

### 4-1. 기준온도는 "참값"이 아니라 모델 파라미터다

이 세션에서 가장 중요한 깨달음이다.

```
당근   논문 4 · 4.44 · 6      기관마다 다름
양파   논문 1.76 · 2 · 5
무     NARO 2024 는 0℃ 로 잡음
```

리뷰 논문이 값을 **범위로** 제시한다. 연구자가 목적에 맞게 고르고 목표값을 함께 산출한다.

→ **핵심은 "어느 값이 맞느냐"가 아니라 "목표값과 누적을 같은 base 로 맞추느냐"다.**
우리는 11작물의 목표값을 역산하므로, base 선택의 영향은 상당 부분 상쇄된다.
남는 차이는 계절·지역·연도가 바뀔 때의 전이 정확도뿐이다.

이 논리가 "호냉성 5℃ 통일" 같은 실용적 선택을 정당화한다. 당근 4~6 범위 안에서 5를
고르는 것은 근거 있는 선택이다.

### 4-2. 지역은 자유 선택이어도 된다

벼 문서의 지역별 일수표가 그걸 보여준다.

```
지역   조생종  중생종  중만생종
중부    50일   53일   57일
호남    52일   55일   60일
영남    50일   54일   58일
```

**일수는 지역마다 다른데 적산온도 목표값은 하나다.** 지역 차이가 적산으로 자동 흡수된다.

→ 역으로, **날짜 기반 판정은 지역이 자유로워지면 틀린다.**
`Safe-farm/src/features/growth/domain/growthStage.ts` 가 `startDay: 21` 식으로
날짜 판정을 하는데, 상추 `totalDays: 45` 가 김제와 대관령에서 같을 리 없다.
최대 20% 벌어진다. GDD 로 바꿔야 하는 실질적 이유가 이것이다.

### 4-3. 일본 자료를 주력으로 안 쓴 이유

작물 적합성은 일본이 낫다(배추·무·파·시금치가 다 있고 기후·품종이 가깝다).
그런데 둘이 걸린다.

```
단일 표준표가 없다    NARO 2024 는 무·양배추에 base 0℃. 기관·논문마다 다름
일평균 정의가 다르다   일본 기상청도 24시간 평균. 우리 스키마는 (Tmax+Tmin)/2
```

→ **배추·파처럼 논문에 없는 작물을 메우는 용도로는 여전히 유효하다.** §5-4 참조.

로드맵 §8 과 같은 취지다. **원인이 거의 같다 — 좁게 보고 단정했다.**

### 6-1. 좁은 어휘로 검색해 기준온도를 절반 넘게 놓침

`생육최저온도` · `발아최저온도` 세 가지 항목 이름만 찾았다.
문서들이 같은 뜻을 다른 말로 쓴다는 걸 놓쳤다.

```
"10℃ 이하에서 생육정지"        ← 옥수수. 놓침
"5℃ 이상에서 자라기 시작함"     ← 감자. 놓침
"최저온도 | 10℃" (표)         ← 미나리. 놓침
```

**6종 → 13종.** 어휘를 넓히고 문장형까지 훑어서 두 배 이상 나왔다.

### 6-2. 정규식이 `씨뿌림` 을 못 잡음

`씨뿌리` 로 찾았는데 실제 작업명은 `씨뿌림` 이다. 세 글자가 다르다.
무·시금치·당근·마늘의 파종 데이터를 "없다"고 잘못 보고했다.

### 6-3. 벼 작업명이 `모내기때`

'이앙' 도 '심기' 도 안 들어 있다. 벼 파종 시기를 못 잡았다.
잡고 보니 생육 단계가 통째로 있었다(§5-2).

### 6-4. 작형 짝짓기 실패 — 봄배추 324일

배추·무·상추·감자·당근은 한 문서에 봄·가을 작형이 **라벨 없이 섞여** 있다.
기계가 첫 파종과 마지막 수확을 집으니 "1월 파종 → 12월 수확" 이 나왔다.
→ `선정작물/select.py` 의 `SPEC` 에 작형별 시작월·수확월을 사람이 못 박았다.

### 6-5. 재배일수를 구간의 양 끝으로 잼

```
봄배추  파종 시작 ~ 수확 종료   142일   ❌
       파종 중앙 ~ 수확 중앙    86일   ✅
```

앞은 "1월 중순에 뿌린 포기가 6월 초에 수확될 때까지"이지 한 포기가 자라는 날이 아니다.

### 6-6. 토마토를 "전부 시설"로 오판

9작형을 보고 전부 시설이라고 단정했다. `정보구분` 칸에 작형 이름이 있는 걸 못 봤다.
실제로는 `조숙재배` · `고랭지재배` · `비가림재배` · `억제재배` 가 노지계다.
가지도 `봄재배(조숙,노지)` 가 있다.

→ **작형 라벨이 `정보구분` 칸에 있다.** 다만 붙어 있는 건 11종뿐이고
나머지는 단일 작형이라 이름·시기로 사람이 판단해야 한다.

### 6-7. 채소 숙기가 "0건" 이라고 보고

당시 `품종_숙기.csv` 가 260행이었다. 파서를 고친 뒤 2,599행이 되었고
숙기가 채워진 행이 **16% → 54%** 로 늘었다. 출처를 `코드`/`주요특성`/`본문`
셋으로 나눈 게 핵심이었다. 상추·배추·수박·토마토에 값이 생겼다.

### 6-8. ⚠ 13~18월 표기 — 데이터 자체의 함정

`농작업시기.csv` 의 종료월이 13~18인 행이 90건 넘게 있다. **오류가 아니라 해를 넘긴 표기다.**

```
13=1월  14=2월  15=3월  16=4월  17=5월  18=6월

마늘   월동기  12월상~14월중   →  12월 상순 ~ 이듬해 2월 중순
파프리카 수확   11월중~18월하   →  11월 중순 ~ 이듬해 6월 하순
```

마늘·양파·보리·시금치 등 월동 작물이 전부 이 표기를 쓴다.
그냥 쓰면 기간 계산이 깨지고 적산 시작일이 틀린다.

### 6-9. 논문 저자를 잘못 인용할 뻔함

`보관/문서/gdd 관련 대화 기록.md` 가 "one equation, two interpretations" 를
**Snyder (1997)** 로 적고 있다. Paredes et al. 이 인용한 것은
**McMaster and Wilhelm (1997)** 이다. 그 문서의 서지정보는 믿지 말 것.

### 6-10. 조건부 계산식 전환은 기각됐다

⚠ **이것과 §1-1 의 Modified 채택은 다른 얘기다. 헷갈리지 말 것.**

```
기각한 것   날씨를 보고 **날마다** 식을 갈아끼우는 것
채택한 것   식은 Modified 하나로 고정. 갈리는 것은 작물의 upper_temp 데이터뿐
```

아래 이유 셋은 전부 "날마다 바뀌는" 데서 나온다. 식을 고정하면 ①②③ 모두 안 생긴다.

"평상시 일반 GDD, 폭염·한파 때 Modified" 를 검토했다가 기각했다. 이유 셋.

```
① 두 식은 평상시에도 갈린다
   상추 base 4.0, 4월 Tmax 18/Tmin 2 →  Standard 6.0 vs Modified 7.0
   폭염도 한파도 아닌 평범한 봄날이다. 45일이면 목표의 9%

② 전환 지점에서 숫자가 튄다
   Tmax 32.9 → 18.45 / Tmax 33.0 → 17.00.  0.1℃ 차이로 1.45 가 튄다

③ gdd_target 은 고정값이다
   누적 규칙이 날마다 바뀌면 그 합계가 목표와 같은 자로 잰 값이 아니게 된다
```

→ 상한이 필요하면 **조건부가 아니라 `upper_temp` 고정 규칙**으로 건다. §1-1.

⚠ ①의 예시(`상추 Standard 6.0 vs Modified 7.0`)가 §1-1 이 한때 적었던
  "Modified 를 쓰면 거의 안 쌓인다" 와 정면으로 어긋났는데 아무도 못 봤다.
  **한 문서 안에서 같은 수치가 반대로 적혀 있으면 둘 중 하나는 틀린 것이다.**
  2026-09-16 에 §1-1 쪽이 틀린 것으로 판명됐다 (§1-1a).

### 6-11. 고온 피해를 적산에 접어 넣지 않는다

폭염을 GDD 안에 흡수시키면 농민 화면에 "진행이 더뎌요" 만 남고 **"폭염 경보" 가 사라진다.**
`재해규칙/결과/disaster_rules.csv` 에 고온해 규칙이 32행 있다. 따로 낸다.

MRCC 도 같은 생각을 한다 — SDD(Stress Degree Days)를 GDD 와 **별도로** 쌓는다.
