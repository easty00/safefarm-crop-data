## 1. 적산온도 계산 방식 — 가장 중요한 함정

한국 농업에서 쓰는 방식이 **세 가지**로 갈린다. (요청서 B-3에서 잡아낸 내용, 검산 결과 타당)

```
① 단순적산온도    Σ(일평균기온)                       모든 날 더함
② 적산온도(관행)  Σ(일평균기온), 기준온도 이상인 날만   빼지 않고 거르기만
③ 유효적산온도    Σ(일평균기온 − 기준온도)             빼기. 국제적으로 GDD라 부르는 것
```

**핵심 함정**: 농진청이 공표한 유일한 목표값(벼 벼베기 적기 = 출수 후 적산온도 1,100~1,200℃)은
**② 단위**다. 검산: 출수 후 50일 × 등숙기 평균 22℃ ≈ 1,100 ✅ / base 7℃를 뺀 ③으로는 750 ❌
(품종별 등숙적산온도 오대벼 1,194·일미벼 1,138 등도 모두 ② 단위와 부합)

→ **이 숫자를 GDD 목표값으로 그대로 쓰면 안 된다.** ③으로 가려면 우리가 다시 역산해야 하고,
그러면 그 값의 출처는 "농진청"이 아니라 "우리 역산"이 된다.

**뒷받침 근거 추가(3판)** — 재해예방정보에 실린 `벼 생육 시기별 최적 및 최저·최고 한계온도`
(1997, 李 등) 표에서 등숙기 최적이 21~22℃다. 위 검산에 쓴 22℃와 독립적으로 일치한다.

### 방식 결정 규칙

- 계산 방식은 **작물별로 `sum_method` 컬럼에 명시**한다 (`simple` / `threshold` / `gdd`)
- 한 작물 안에서, 또는 한 화면 안에서 두 방식을 섞지 않는다
- 작물 간에 다른 방식을 쓰는 것은 **허용**한다. 벼처럼 농진청 공식값이 있으면 ②를 써서 출처를
  살리는 게 낫고, 채소처럼 공식값이 애초에 없으면 어차피 ③ 역산이다
- 농민 화면에는 방식 이름을 노출하지 않는다. "적산 n / 목표 m"만 보여준다

### 상한온도(Modified)는 별개의 축이다

이전 논의에서 "표준 GDD는 상한=∞인 특수케이스이므로 Modified 하나로 통일하면 된다"고 정리했는데,
그 논리는 **③ 안에서만** 성립한다. ②와 ③의 차이(기준온도를 빼는지)는 그 논리로 통합되지 않는다.
정확히는 두 개의 독립된 설정이다.

```
축 1  누적 방식        ① / ② / ③        sum_method
축 2  고온 상한 적용    없음 / 상한온도    upper_temp (nullable)
```

상한온도는 폭염일이 많은 작물·시기에서 "더워도 안 자라는" 구간을 반영한다. 자료가 없는 작물은
비워두면 상한 미적용으로 동작한다.

### ⚠ 한계온도와 기준온도는 다른 숫자다 (3판에서 추가)

재해예방정보에서 작물별 **한계온도**를 대량으로 확보했다(§2-3). 쓸모가 크지만 **적산온도
계산의 `base_temp`로 그대로 쓰면 안 된다.**

```
한계온도   그 온도 아래/위로 가면 "피해가 난다"        → 재해 경보 판정용
기준온도   그 온도 아래에서는 "생육이 진행되지 않는다"  → 적산온도 계산용
```

예: 배추 냉해온도 -8℃는 배추가 -8℃까지 자란다는 뜻이 아니다. 두 축을 섞으면 적산이 전부
어긋난다. 저장할 때도 컬럼을 나눈다 — `base_temp`(계산용)와 `damage_low`/`damage_high`(판정용).

### 2-7. 문서 판독 도구 — 형식 다섯 가지

**확장자를 믿지 않는다. 파일 앞 4바이트로 판정한다.** 이름과 내용이 어긋난 파일이 실제로 있다
(`.pdf` 이름의 JPEG 3건).

| 앞바이트 | 형식 | 방법 | 상태 |
|---|---|---|---|
| `%PDF` | PDF | pypdf. 쪽 표시 `===== p.N =====` 삽입 | ✅ |
| `PK` | hwpx (ZIP+XML) | `Contents/section*.xml` 파싱 | ✅ 가장 깨끗함 |
| `D0CF11E0` | hwp (OLE) | olefile + zlib(-15) + `HWPTAG_PARA_TEXT`(67) | ✅ |
| `HWP ` | **한글 3.0 구형식** | 2바이트 리틀엔디안 → johab 변환 | ⚠ 건져내기 수준 |
| `FFD8FF` 등 | 사진 | 글자 없음. 실패가 아니라 따로 센다 | — |

한글 3.0은 문단 구조까지 해석하지 않고 글자로 읽히는 구간만 이어붙인다.
3건 중 2건은 잘 나왔고(2,381자 / 1,855자) 1건은 37자만 건졌다.

표는 **칸 경계를 `|`로 살려둔다.** 지우면 숫자가 한 덩어리로 붙어 못 읽는다.

저온요구도 7.2℃      단위가 시간(chill hours). 휴면 타파용이지 생육 누적이 아니다
발아 적산온도 140~150 싹틀 때까지만의 값. 생육기간 목표값과 자리가 다르다
침종 적산온도 100     볍씨를 담근 '물' 의 누적온도. 생육과 무관
```

`sumtemp.py` 가 이 셋을 이미 갈라 두었다. **`적산온도.csv` 의 `쓸모` 칸을 보고 쓸 것.**

### 2-9. 품종 단위 재배 적지 온도 — 새로 찾은 것

품종요약서의 `적응 지역` 절에 이런 문장이 있다.

```
밀 아리진흑       1월 최저 평균기온 -8℃ 이상 지역(산간 고령지 제외)
귀리 중모2511     1월 평균최저기온 -6℃ 이상 (중산간지 제외)
트리티케일 옹골진   1월 최저평균기온 -10℃ 이상인 지역
```

과수 동해 한계온도표(작물 단위)보다 **한 단계 세밀한 품종 단위 기준**이다.
`품종정보/결과/적응지역_온도.csv` 로 뽑아둔다. 겨울작물(밀·보리·귀리·트리티케일)에 몰려 있다.

### 2-10. 미확인 승인 서비스

농업용어사전(쉬운 말 변환), 공공데이터, 농사로 공통코드, 농업기술더하기나누기,
농작업안전교육, 사진마당원화정보, 이달의농업기술.

## 3. 수집 방침 — 전수 수집 후 선별

작물을 미리 좁히지 않는다. **전수 수집 → 분류 → 쳐내기** 순서로 간다.
(요청서 A-3은 6작물 8행으로 한정하고 있으나, 이 방침과 상충하므로 수집 단계에서는 적용하지 않는다)

이유: 수집 자체는 비용이 거의 없고, 어떤 작물이 쓸 만한지는 데이터를 본 뒤에야 판단할 수 있다.

**3판에서 실제로 지킨 것**: 품종정보를 논벼 50건이 아니라 2,599품종 전체로 받았고,
화훼 839건도 포함했다. 노지와 거리가 멀어 보여도 받는 순서만 뒤로 미루고 버리지 않았다.

## 6. 판단과 주의사항

### 6-1. 저장 스키마 — `source`·`confirmed` 필수

요청서 E안을 채택하되, 3판에서 재해 판정용 컬럼을 계산용과 분리한다.

```
crops.csv          crop_id · name · farm_type · variety · sum_method
                   base_temp · base_temp_source · upper_temp · upper_temp_source
                   target_sum · target_sum_source
                   sow_from · sow_to · harvest_from · harvest_to · days_std
                   source · confirmed(Y/N)
crop_stages.csv    crop_id · stage_order · stage_name · sum_from · sum_to
                   days_from · days_to · guide · source · confirmed
crop_schedules.csv crop_id · work_type · month_from · period_from · month_to
                   period_to · region · note · source
disaster_rules.csv crop_id · disaster · stage · metric · op · value · unit
                   action · source · confirmed
                   ← 한계온도·감수율표가 여기로 간다. base_temp 와 섞지 않는다
orchard_fit.csv    crop_id · metric · op · value · unit · source
varieties.csv      crop_id · variety_name · maturity · breed_year · institute
                   heading_date · maturity_date · source · confirmed   (3판 추가)
data/raw/          API 응답 원문 (값이 이상할 때 추적용)
```

`confirmed`: `Y` = 1차 자료로 확인, `N` = 역산·추정·참고값. 심사에서 "이 숫자 어디서 났냐"는
질문에 정직하게 답하기 위한 장치다.

`source` 표기 예 — PDF는 쪽 번호까지 적을 수 있다.

```
"농진청 재해예방정보 2026년 제9호 p.77 (1997, 李 등)"
"농작업일정 첨부 '고추 농작업일정.hwpx' 환경관리 절"
"편차최소화 추정"                                  ← confirmed=N
```

### 6-2. 목표 적산온도 역산 절차

```
① 작물별 대표 지역(주산지) 관측소 선정
② 농작업일정에서 파종·수확 시기 추출
③ 순(旬) → 날짜 변환: 상순 5일 · 중순 15일 · 하순 25일 (통일)
④ 기상청 일통계로 그 기간 일평균기온 확보 (결측은 null이 아니라 -999)
⑤ sum_method에 따라 누적
⑥ 최근 10년 반복 → 평균 = 목표값, confirmed=N
```

### 6-3. 기준온도 추정 — 방법은 실재하나 입력이 약하다

지역별 날짜가 있으면 "기준온도가 맞으면 지역이 달라도 목표값이 비슷해야 한다"를 이용해
base를 0~15℃로 바꿔가며 지역 간 편차가 최소인 값을 채택하는 방법이 있다.

이 기법 자체는 문헌에 실재한다. **다만 원래 기법은 "관측된 생물계절 날짜"를 입력으로 쓴다.**
농작업일정의 "8월 상순~하순"은 관측값이 아니라 권장 범위이고, 중앙일은 우리가 만든 가정이다.
따라서 결과는 참고값 수준으로 보고 반드시 `confirmed=N`,
`base_temp_source="편차최소화 추정"`으로 남긴다.
벼(지역별 일수가 명시된 유일한 작물)로 먼저 시험한다.

### 6-4. 적산온도로 풀리지 않는 작물

```
과수(단감·포도·사과 등)   겨울 휴면 → 봄 발아. 심은 날부터 누적하는 모델이 아님.
                        냉각요구시간(chill hours) + 발아 후 온도요구를 따로 계산해야 함.
                        "단감 13℃ / 2,340시간"은 적산온도가 아니라 적지 판정용 기후값.
                        1차에서는 적산 진행률이 아니라 적지 판정 + 연간 달력으로 접근.
마늘                     쪽 분화에 5℃ 이하 30일 이상 필요(저온 요구도). 적산만으로 판정 불가.
```

과수는 §2-3의 `과수 겨울철 한계온도`로 **동해 경보**는 지금도 만들 수 있다.
사과 만개기 -1~-2℃ 같은 값은 생육단계와 묶여 있어 바로 규칙이 된다.
포도 적지 조건은 여전히 미확보다. 농작업일정 첨부 hwpx(§2-1c)에서 찾아야 한다.

```

## 8. 실수 기록 — 같은 함정을 다시 밟지 않기 위해

방법이 틀렸던 것들이다. 결과만 적으면 왜 그렇게 정했는지 잊는다.

### 8-1. 제목 태그를 하나만 보고 자름

`재배법.csv`를 `<h2>` 기준으로 잘랐는데 `workScheduleDtl`은 `<h3>`를 쓴다.
`<h2>`는 달력 소유다. 그대로 돌렸으면 **표가 통째로 비었을 것**이다.
→ `<h[234]>` 전부로 자르고, 제목 없이 앞에 붙은 내용도 `(머리말)`로 남긴다.

### 8-2. 정규식으로 걸러 읽음

"숫자 + 단위 + 비교말" 패턴으로 본문을 훑었다. 그래서 **가장 값진 자료 셋을 전부 놓쳤다.**

```
벼 생육시기별 한계온도표   → 표라서 문장 패턴에 안 걸림
가루쌀 적산온도 700℃부터   → '부터'가 비교말 목록에 없었음
침관수 감수율표           → 역시 표
```

→ 본문은 필터 없이 전문을 저장하고 통독한다. 필터는 찾기 보조일 뿐 읽기 방법이 아니다.

### 8-3. `|`로 이어진 목록을 통째로 씀

`fileName`과 `downUrlList`가 둘 다 판본 목록인데 나누지 않고 붙여 썼다.
`.pdf`로 끝나는 이름의 파일에 hwpx 알맹이가 담겨 판독이 전부 실패했다(0자).
→ 짝을 맞춰 나누고, 저장 후에도 앞 4바이트로 형식을 다시 확인한다(27,810자로 복구).

### 8-4. 표본 하나로 서비스 전체를 단정

재해예방정보를 2026년 하나만 보고 "월간 회보다 / 구조화 테이블 없다 / 한파 자료 없다"고
결론냈다. 셋 다 틀렸다(§2-3).
→ 연도·분류를 넓혀 목록부터 세어보고 나서 판정한다.

### 8-5. 코드 구분을 안 갈라서 육성년도를 작물로 셈

`middleCategoryList`는 `gubn`이 `CLASS1`/`CROP`/`YEAR`로 섞여 나온다.
이걸 안 가르고 2016~2025년을 작물 코드로 조회해 품종 0건이 나왔다.
→ `gubn == "CROP"`만 쓴다.

### 8-6. 오류 응답을 캐시에 저장

"그런 건 없다"는 응답을 정상인 줄 알고 저장해두면 다음 실행 때 건너뛰어 영영 모르게 된다.
→ `resultCode != 00`이면 저장하지 않는다. 0바이트 파일도 지우고 다시 받는다.

### 8-7. 서버가 확장자로 막는 것을 파일 부재로 오해

재해예방정보 첨부 92건이 HTTP 400으로 실패했다. 연도 문제로 보였으나 **`.hwpx` 확장자를
서버가 막는 것**이었다. 성공한 `.hwp` 주소의 확장자만 바꿔도 400이 났다.
→ 실패가 몰릴 때는 공통점을 먼저 센다. 해결은 §2-3 끝.

### 8-8. 제목으로 연도를 대조하려다 두 번 실패

```
재해예방정보  표 제목으로 대조 → '1997'/'‘97', '이'/'李', '및'/'과'/'와' 가 달라
                             같은 표가 다른 표로 세어짐. 2023년 23가지 vs 2026년 90가지
주간농사정보  항목 제목으로 대조 → 기상도 범례('2℃ 초과' 106회)를 잔뜩 물어
                             "겹침 53%"라는 무의미한 숫자가 나옴
```

→ **제목은 대조의 열쇠로 못 쓴다.** 본문 문장을 직접 맞대야 한다.
주간농사정보를 그렇게 다시 재니 겹침이 21%로 나왔고, 결론이 정반대로 뒤집혔다.

### 8-9. 파서를 한 호만 보고 만듦

병해충 요약표 파서를 제10호 하나만 보고 만들었다. 2023~2024년을 절반 넘게 놓쳤다
(269행 → 고친 뒤 1,339행). 실제로는 네 가지 모양이 섞여 있었다.

```
① 한 줄에 둘    ▶ (주 의 보) 병 : 붉은곰팡이병 / 해충 : 열대거세미나방
② 여러 줄로     ▶ (예   보)  다음 줄에  - 병 : …  - 해충 : …
③ 구분 없이     ▶ (주의보) : 노균병(양파), 흑색썩음균핵병(마늘, 양파)
④ 줄바꿈 이어짐  … 노균병, 역병,   다음 줄에  딸기 꽃곰팡이병
```

구분도 병·해충만이 아니라 **바이러스**가 따로 있었다.
그리고 쉼표로 그냥 쪼개면 `잎마름병(마늘, 양파)` 가 `잎마름병(마늘` + `양파)` 로 갈린다.
**괄호 밖 쉼표에서만 쪼개야 한다.** 괄호 안은 대상 작물이라 따로 칸을 만들어 담았다.

→ §8-4와 같은 실수다. 형식을 단정하기 전에 **여러 해·여러 호를 먼저 펼쳐 본다.**

## 9. NCPMS — 같은 자료인가, 다른 자료인가

NCPMS(국가농작물병해충관리시스템, `ncpms.rda.go.kr`)에도 우리가 받는 자료가 올라온다.

**⚠ 아래는 NCPMS 웹페이지(`/npms/Main.np`, `/npms/OpenApiInfo.np`)를 읽은 것이다.
NCPMS API 를 실제로 부른 것이 아니다.** NCPMS는 농사로와 별도 키가 필요하고
(로그인 회원만 신청 가능) 우리는 아직 없다. 실측이 아니므로 단정하지 않는다.

| 자료 | 농사로 API (우리가 쓰는 것) | NCPMS |
|---|---|---|
| 주간농사정보 | 870건 원본 | **같은 파일** (§2-4에서 해시로 확인) |
| 재해예방정보 | 112건 원본 | 같은 계열 |
| 병해충 발생정보 | 257건 PDF 원본 | 같은 회보 + 화면으로 정리 |
| 병해충 도감 | 없음 | 있음 (식량/과수/화훼/채소/특용/잡초) |
| 예찰 실측 | 없음 | 있음 (일자별·시군별) |
| **발생 예측** | **없음** | **있음 (GIS 기반 지도, 지점별 시계열)** |

**문서 자료는 상위호환이 아니라 같은 것이다.** NCPMS 화면의 경보/주의보/예보 목록은
우리가 §2-5에서 PDF로 받은 바로 그 회보의 첫 쪽이다. NCPMS는 그것을 작물-병해충 쌍으로
미리 쪼개 보여줄 뿐이고, 우리는 파서로 같은 결과(1,339행)를 얻었다.

**진짜 차이는 예찰·예측이다.** 농사로에는 아예 없다. 다만 이것은 기상·위성 담당자의
영역과 맞물리므로, 가져올지 여부는 이 로드맵 단독으로 정할 일이 아니다.

→ 판단: 도감·회보는 이미 있으니 **예찰·예측 API 만** 키를 신청해 실측해 본다. 급하지 않다.
