
⚠ **표를 복사하기 전에 저쪽을 먼저 고쳐야 하는 것이 둘 있다.** 순서를 지킨다 —
   표만 먼저 넣으면 적재가 깨진다.

```
1  crops.upper_temp 칸이 저쪽에 없다
   ALTER TABLE crops ADD COLUMN upper_temp NUMERIC(4,1);   -- nullable
   문장은 ../GDD계산관련/GDD_작업인계.md §85

   ⚠ 함정 — out/스키마/crops.csv 에는 이 칸이 **없다.** 저쪽 ORM 이 받는 칸만 내기로
     했기 때문이다(build.py 의 `계약`). 값은 out/스키마/근거/crops.csv 에 11행 다 있다.

     안 그러면 축 2(고온 상한)가 통째로 조용히 사라진다.

2  gdd_target 19행이 비어 있다 — 저쪽에서 계산할 값이다
   저쪽 crop_variants.gdd_target 은 NOT NULL 이라 **비운 채로는 적재가 안 된다.**
   nullable 로 바꾸든, 계산해 채운 뒤 적재하든 둘 중 하나를 먼저 정해야 한다.

   ⚠ **그때 days_to_harvest 도 같이 가른다.** 지금 벼·감자·양파·수박은 숙기를
     셋으로 갈라놓고 수확일수가 세 행 모두 같다. gdd_target 을 채우는 작업과
     한 번에 푸는 것으로 정했다 (2026-09-16). 따로 고치면 같은 자리를 두 번
     만지게 되고, 둘이 어긋나면 어느 쪽이 맞는지 알 수 없다.
     할 일 목록은 ../확인필요.md §6 에 있다 — 수박은 원문에 답이 있다.

3  crop_disaster_rules 표가 저쪽에 아예 없다
   ORM 초안 = 제안_crop_disaster_rule.py. 그 파일 머리에 같이 고칠 네 곳이 적혀 있다.
   ⚠ 저쪽의 기존 `disaster_rules` 와 **다른 표다.** 저쪽은 관측소별 절기 기상 통계,
     이쪽은 작물 생리 기준. 이름이 비슷해 섞기 쉽다.
```

`근거/` 를 안 넘기는 이유 — 같은 행에 `source` · `confirmed` · `출처들` 이 붙어 있다.
적재용이 아니라 "이 숫자 어디서 났냐" 에 답하는 쪽이다. 여기 남겨두고 물어볼 때 연다.

`verify.py` 는 저쪽 검사를 그대로 옮긴 것이다. **여기서 통과 = 저기서 적재 성공**이 목적이다.
저쪽이 바뀌면 여기도 같이 고쳐야 한다.

### §A 와 §B-2 가 어긋난다던 것 — 어긋난 게 아니다

`spec.py` 가 **등록표(`crops.py`)에 있는 작물만** 읽도록 고쳤다. `온도()` 와 `작형()` 둘 다.

```

```

그래서 §A 가 §B-2 보다 줄이 많아도 맞다. 지금 §A 22행 중 18행이 읽힌다.

### 작물을 넷 버렸다

`당근 · 파 · 쪽파 · 가지` — 다섯 원본 날 자료를 전부 세어 정했다.
당근·파·쪽파는 재해·단계·고온·경보·숙기가 **모두 0**이고 달력밖에 못 준다.
가지는 재해 1건뿐이고 base_temp 도 미결이었다.

```
작물 13 = 본선 11 + 확인용 2   ·   등록 문서 17개
```

⚠ **수와 목록을 문서에 적지 않는다.** `python pipeline/crops.py` 로 본다.
예전에 "14작물" 이 20개 파일 70여 곳에 박혀 있다가 한꺼번에 낡았다.
CSV 칸 `14작물` → `본선`, 정본 파일 `14작물_확정표.md` → `작물_확정표.md` 로 바꿨다.
